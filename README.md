# BHAIRAV ENGINE (B-ENGINE)

## A Structured Bio-Design & Innovation Methodology

**BHAIRAV ENGINE (B-ENGINE)** is an evidence-aware, human-centered and
iterative bio-design and innovation engine for healthcare, medical
technology, digital health, diagnostics, clinical technologies, public
health, clinical services, health businesses, biomedical engineering,
and extreme-environment and space-health technologies.

B-ENGINE helps users move from a **Stimulus, Need, Problem, Idea,
Dataset, Technical Concept, or desired End Product** toward a
structured, testable, evidence-supported and implementable solution.

> **Organize → Structure → Create Artifacts → Collect Evidence → Apply
> Frameworks → Match Evidence → Receive Feedback → Iterate → Validate**

------------------------------------------------------------------------

## The Core B-ENGINE Principle

B-ENGINE uses:

**One common Framework Bank + persistent DFV attitudes + evolving
evidence.**

There are **not separate framework banks for IDENTIFY, INNOVATE and
IMPLEMENT**. The same frameworks can be used repeatedly as the project
and its evidence mature.

> **Frameworks persist. Evidence changes. Answers evolve. Match is
> corrected.**

The phases represent project and evidence maturity; they do not
determine which frameworks are available.

------------------------------------------------------------------------

## The Three DFV Attitudes

Every project can be examined through three persistent attitudes:

### D --- DESIRABLE

Does someone actually want, need, understand, accept or benefit from
this?

This includes user and patient needs, clinical needs, experience,
usability, accessibility, adoption, stakeholders, social value and
government/public-health interest.

### F --- FEASIBLE

Can it actually be scientifically, technically and operationally
achieved?

This includes science, engineering, technology, design, performance,
safety, manufacturing, infrastructure, regulation and operations.

### V --- VIABLE

Can it sustainably exist, operate and deliver value?

This includes economics, cost structure, business model, buyer, payer,
procurement, reimbursement, organization, marketing, market,
sustainability and policy.

**DFV is continuous across all phases:**

**IDENTIFY → INNOVATE → IMPLEMENT**

## Evidence-Driven, Not Framework-Driven

The intelligence of B-ENGINE comes from matching frameworks against an
evolving evidence state.

### Past / Accumulated Data

Examples include:

-   Literature
-   Guidelines
-   Patents
-   Existing products
-   Historical projects
-   Benchmarks
-   Regulations
-   Case studies
-   Previous experiments
-   Known failure modes
-   Wisdom cases
-   Existing datasets

Past data provides **context and precedent**.

### Present / Real-Time Data

Examples include:

-   Interviews
-   Observations
-   Measurements
-   Experiments
-   Prototype testing
-   User testing
-   Pilot data
-   Costs
-   Field observations
-   Safety events
-   Current market feedback

Present data provides **current project evidence**.

> Historical or generic information should never be presented as current
> project evidence.

## The B-ENGINE Core Components

Every project may contain:

**Stimulus → Variables → Metrics → Frameworks → SCALEs → Artifacts →
Match → Feedback → Iteration**

### Stimulus

A **Stimulus** is the source of inspiration, observation or starting
point.

It may be a:

-   Clinical problem
-   Patient story
-   Doctor complaint
-   Research paper
-   Patent
-   Existing device
-   Object
-   Image
-   Natural system
-   Environment
-   Failure
-   Business problem
-   Dataset
-   Technical concept
-   Desired end product

A stimulus can provide inspiration, properties, analogies, questions,
variables, metrics, frameworks, possible mechanisms and possible design
directions.

**A stimulus is not automatically evidence.** Stimulus-derived analogies
or ideas remain an analogy, hypothesis or inspiration until supported by
appropriate evidence.

### Variables

Variables are properties, features, conditions or constraints relevant
to the project.

They may be clinical, technical, biological, behavioral, environmental,
economic, regulatory, operational, social, ethical or safety-related.

Important variables can be described by:

  Field         Description
  ------------- -------------------------------------------------------------
  Name          Variable name
  Description   What it represents
  Type          Qualitative / quantitative / ordinal / binary / categorical
  Source        Where it came from
  DFV           Desirable / Feasible / Viable
  Role          Design variable / constraint / outcome / confounder
  Status        Known / estimated / assumed / missing / requires validation

### Metrics

A metric is a measurable or structured indicator derived from variables.

Where valid, B-ENGINE encourages conversion of variables into measurable
metrics. A metric may include definition, formula, unit, measurement
method, baseline, target, direction of improvement, frequency, evidence
source, confidence and safety relevance.

Numbers should not create false precision. Values should be identified
as, for example:

-   Measured value
-   Literature value
-   Benchmark
-   Proposed target
-   Assumption
-   Estimate
-   Illustrative value

## The Framework Bank

A **Framework** is a structured way to **ask, organize, compare,
interpret or decide** about data.

It can be used with qualitative or quantitative data, past or real-time
data, variables or metrics.

B-ENGINE maintains **one universal Framework Bank** across all phases.

The Framework Bank is organized into:

### Desirability

Understanding users, needs and adoption.

Examples: Empathy Map, Patient Journey, Persona.

### Feasibility

Understanding technical, clinical, safety and regulatory requirements.

Examples: Root Cause Analysis, Benchmarking, FMEA, System Architecture.

### Viability

Understanding economic, business and implementation requirements.

Examples: Business Model Canvas, Cost Model, Unit Economics.

### Matching / Decision

Comparing evidence against requirements or alternatives.

Examples: Gap Analysis, Decision Matrix, Risk Matrix, Evidence Grading.

### Wisdom

Bringing lessons, experience and accumulated knowledge into decisions.

Examples: Lessons Learned, Historical Failure Analysis, Assumption
Review.

> **The framework does not define the phase --- the question and
> evidence requirement determine which framework is used.**

Framework selection follows:

**Current question → Required evidence → Variables → DFV relevance →
Framework → Artifact → Match**

If a framework is explicitly provided by the user, B-ENGINE does not
replace or modify it unless modification is requested.

------------------------------------------------------------------------

## SCALE

A **SCALE** is a bumper pack of frameworks with pre-filled or suggested
variables, metrics and supporting knowledge for a particular product,
service or problem category.

A SCALE may contain:

-   Frameworks
-   Variables
-   Metrics
-   Example data
-   Questions
-   Constraints
-   Risks
-   Pre-formed or pre-designed artifacts
-   Match criteria
-   Wisdom
-   Decision gates

### SCALE ≠ Framework

A Framework is one structured method.

A SCALE is a collection of relevant frameworks and supporting
information configured around a particular product, service or problem.

### SCALE ≠ Final Answer

A SCALE provides a starting structure. It must not override
project-specific evidence.

## How a User Enters B-ENGINE

B-ENGINE provides two primary starting choices.

### Option A --- Use a Pre-Designed SCALE

The user selects a SCALE relevant to their product, service, problem,
clinical area, technology or environment.

The SCALE provides ready-made frameworks, variables and metrics, which
can then be modified according to the actual project.

### Option B --- Start Fresh

The user starts with a:

**Stimulus / Need / Problem / Idea / End Product**

and manually adds relevant:

-   Frameworks
-   Variables
-   Metrics
-   SCALEs
-   Constraints
-   Artifacts

B-ENGINE helps determine what is missing.

## The Three Phases

B-ENGINE has three major phases:

**IDENTIFY → INNOVATE → IMPLEMENT**

They represent stages of project and evidence maturity. They are **not
separate framework worlds**.

### 1. IDENTIFY

Identify and understand the problem, opportunity, target and relevant
DFV dimensions.

Identify examines:

-   Who has the problem?
-   What is the problem?
-   How important is it?
-   What is the current experience?
-   What is painful, unsafe, slow or inaccessible?
-   Who are the stakeholders?
-   What unmet need exists?
-   What causes the problem?
-   What technical and scientific factors matter?
-   What technologies already exist?
-   What constraints and gaps exist?
-   Who is the buyer and payer?
-   What economic, operational, procurement or reimbursement issues
    exist?

#### Identify Match

> **Identify Match measures how much of the selected frameworks has been
> populated with identified real/project data.**

It is primarily a **coverage measure**, not proof of correctness,
validity, market acceptance or feasibility.

### 2. INNOVATE

After IDENTIFY, the project has structured information. The user creates
and explores possible solutions.

The process becomes:

**Existing evidence + new data + hypotheses + ideas → framework analysis
→ filtering → testing**

Ideas may come from identified needs, stimuli, existing technologies,
analogies, frameworks, the user or B-ENGINE.

#### Innovate Match

> **Innovate Match compares the hypothesized or proposed solution
> against new real-time evidence.**

Examples of new evidence include:

-   Interviews
-   Experiments
-   Prototype measurements
-   User testing
-   Technical tests
-   Market testing
-   Cost analysis
-   Simulation
-   Literature validation
-   Expert review

The framework may remain the same while the answer changes as new
evidence arrives.

### 3. IMPLEMENT

In IMPLEMENT, a selected solution, device, model, software system,
service or intervention is taken toward implementation and validation.

Additional frameworks may be added when implementation creates new
questions, such as:

-   Regulatory framework
-   Manufacturing framework
-   Clinical validation framework
-   Cybersecurity framework
-   Procurement framework
-   Post-market framework
-   Operational framework

#### Implement Match

> **Implement Match re-evaluates the same framework universe using
> actual implementation, testing, validation and field data.**

The Match is corrected overall rather than restarted from zero:

**Previous Match + new evidence → corrected Match**

------------------------------------------------------------------------

## Match Is Not Automatically "Success"

B-ENGINE must never interpret a high Match percentage as automatic
success.

Every Match must answer:

> **Matched against WHAT?**

A Match requires:

1.  A defined target
2.  A claim, requirement or question
3.  Appropriate evidence
4.  A valid matching method
5.  Known uncertainty

### Match Types

#### Coverage Match

Measures how much of a framework has been populated.

**Coverage = completed relevant items / total relevant items × 100**

#### Threshold Match

Determines whether an actual value meets a predefined requirement.

#### Gap Match

Compares current state against target.

**Gap = Target − Actual**

The direction of improvement must be stated.

#### Similarity Match

Used for user needs, features, narratives, text and requirements.

#### Evidence Match

Measures whether a claim is supported by appropriate evidence.

#### Requirement Match

Measures whether a solution satisfies defined requirements.

#### Field Match

Compares intended performance with actual implementation performance.

------------------------------------------------------------------------

## Evidence Maturity

Evidence supporting a project may mature through:

**Exploratory → Assumption-based → Evidence-informed →
Prototype-informed → Test-supported → Field-informed → Validated for
defined context**

Evidence may also become:

**Contradicted / Requires revision**

B-ENGINE must never silently convert:

**assumption → fact**

or:

**hypothesis → evidence**

``` text

       ↓
IDENTIFY
       ↓
Frameworks + Variables + Metrics
       ↓
Artifacts
       ↓
Real Data
       ↓
MATCH
       ↓
INNOVATE
       ↓
Ideas / Hypotheses
       ↓
Experiments / Feedback
       ↓
MATCH
       ↓
IMPLEMENT
       ↓
Testing / Validation / Field Data
       ↓
CORRECTED MATCH
       ↓
Target Matched?
     ↙       ↘
   YES        NO
    ↓          ↓
IMPLEMENT    FEEDBACK
              ↓
       Earlier phase / new
       framework / new evidence
              ↓
           ITERATE
```

Feedback can enter the pathway at any point.

The important progression is not simply phase movement. It is:

> **The evidence supporting the project has matured.**

## Target Match

Implementation is not necessarily the endpoint.

The actual endpoint is:

**TARGET MATCH**

Target Match means the proposed entity has achieved sufficient
evidence-supported matching against its declared targets for the defined
context.

Targets may include:

-   User needs
-   Clinical requirements
-   Technical requirements
-   Safety
-   Regulatory requirements
-   Economic requirements
-   Operational requirements
-   Market requirements
-   Environmental constraints
-   Sustainability
-   Accessibility
-   Ethics

> **Never invent the target threshold.**

## End-Product-Driven Mode

When the user already knows what they want to build, B-ENGINE can work
backward from the desired end product.

For example:

> "I want to build a portable diabetic neuropathy screening device."

B-ENGINE should:

1.  Define the End Product.
2.  Identify intended users and setting.
3.  Search/select an appropriate SCALE if available.
4.  Allow the user to modify the SCALE.
5.  Identify relevant DFV questions.
6.  Select relevant frameworks.
7.  Identify variables and metrics.
8.  Identify constraints.
9.  Start IDENTIFY.
10. Establish the first Match checkpoint.

------------------------------------------------------------------------

## Problem-Driven Mode

When the user provides only a problem, observation or stimulus, B-ENGINE
can structure the problem before converging toward an end product.

For example:

> "Rural patients have difficulty accessing nerve conduction testing."

B-ENGINE should:

1.  Capture the Stimulus.
2.  Extract properties.
3.  Identify variables.
4.  Identify relevant metrics.
5.  Explore Desirable, Feasible and Viable dimensions.
6.  Select appropriate frameworks.
7.  Generate possible opportunity areas.
8.  Generate candidate solutions where justified.
9.  Test assumptions.
10. Converge toward an End Product based on evidence.

> **Do not prematurely force the problem into a predetermined product.**

## Safety and Responsibility

B-ENGINE must:

-   Never fabricate evidence.
-   Never fabricate clinical performance.
-   Never fabricate regulatory approval.
-   Never fabricate market demand.
-   Never fabricate user feedback.
-   Never convert assumptions into facts.
-   Flag safety risks.
-   Flag regulatory uncertainty.
-   Protect privacy.
-   Distinguish prototype from validated product.
-   Distinguish research from clinical use.
-   Identify where expert review is required.

**Safety, ethics and patient welfare take priority over novelty, speed
or commercial appeal.**

B-ENGINE is a methodology for structuring innovation. It does not
replace clinical judgment, scientific validation, engineering
verification, regulatory review, ethical review or professional
expertise.
